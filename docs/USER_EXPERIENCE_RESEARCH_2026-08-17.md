# 会话能力蒸馏器用户实际体验调研

**调研日期：** 2026-08-17
**对象：** 本机 Codex 会话选择工作台、对话蒸馏器、已生成能力包的独立 Agent
**结论：** 当前系统已经具备本机自动发现、会话选择、项目证据、Skill/MCP/独立 Agent 交付和本地执行入口；但用户最关心的三件事尚未形成闭环：**找对会话、看懂蒸馏结果、立刻打开并使用刚生成的包**。问题不是功能缺失，而是把原始记录、阶段日志和历史产物直接暴露给新手，缺少语义归并、推荐和交付后导航。

## 调研方法与范围

以第一次使用此类产品、不会记忆会话编号、希望一键生成可用能力包的用户为主角，按以下真实路径操作：

1. 打开本机会话工作台，等待自动扫描，选择一条会话。
2. 打开对话蒸馏器，搜索、筛选并勾选会话。
3. 启动一个已生成能力包的独立 Agent，查看首页、模型和工作区设置、能力列表与移动端排版。

本次没有点击“生成能力包”、模型调用、文件修改或命令执行，因此没有新建能力包、修改项目文件或访问外部服务。观察来自正在运行的本机页面和已有能力包，而不是仅阅读源码。

## 已验证的正向体验

| 环节 | 已验证表现 | 用户价值 |
| --- | --- | --- |
| 本机会话发现 | 工作台实际发现 **931** 条本机对话；蒸馏器可自动加载最近会话。 | 不必手动定位 JSONL。 |
| 选择反馈 | 在主工作台选中会话后，页面明确显示“已选择 1 条会话”，并说明会保留标题、路径、哈希和全部事件。 | 用户知道选择已经生效。 |
| 蒸馏器引导 | 蒸馏器首页使用“选择本机对话 -> 查看蒸馏建议 -> 生成能力包”三步说明，且默认勾选 Skill、MCP、独立 Agent。 | 首次用户能理解目标交付。 |
| 搜索 | 在蒸馏器输入“全量解析”后，真实结果由 300 条缩小到 12 条。 | 比主工作台的原生长列表更容易开始。 |
| 独立 Agent | 已生成 Agent 成功加载 **38** 项工具和 **20,294** 条原始记录，并展示模型、工作区、文件修改、命令执行和继续任务入口。 | 交付物不是静态说明，而是可运行本地应用。 |
| 移动端 | 在 390 x 844 视口下，独立 Agent 没有横向溢出。 | 内容不会被裁切到屏幕外。 |

## 关键问题

### P0：会话选择无法支持 931 条真实数据

**实际观察**

- 主工作台把 **931** 条会话放进一个原生多选列表；页面共有 60 个按钮，整个页面高度为 9,023 px。
- 每一项同时混入会话编号、原始首句、运行编号、时间和文件体积。例如第一条以 `019ffb...全量解析这个会话调用了哪些工具...` 开头，体积为 224.5 MB。
- 大量会话以 `/goal ...` 开头，标题几乎相同；用户必须比较很长的原始句子和编号才能判断版本。
- 蒸馏器虽然有搜索，但当前只加载 **300 / 931** 条。搜索“全量解析”后显示 12 条，12 条仍是同一首句的近似副本，只靠时间、运行编号和体积区分。

**用户后果**

用户无法回答“应该选哪一条”。当选择错误版本时，后续蒸馏、能力命名和独立界面都会基于错误的对话，功能越完整，错误成本越高。

**必须重构为**

1. 扫描后自动生成并缓存**语义标题**，不把原始首句作为主标题。
2. 每个会话卡片固定显示：`语义标题`、`项目/主题`、`状态（完成/进行中）`、`最近时间`、`规模`、`版本关系`。
3. 把相同目标的重复会话归为“同一任务链”，默认推荐“最后完成且有验证记录”的版本；保留展开查看全部版本。
4. 会话库必须支持全量 931 条的服务端搜索、分页或虚拟列表，不能把 300 条上限伪装成全量入口。
5. 主工作台和蒸馏器复用同一套会话选择器，避免一个可搜索、一个不可搜索的体验分裂。

**验收标准**

非技术用户给出一句目标（例如“把对话变成 Skill、MCP 和独立 Agent”）后，能在 30 秒内看到“推荐会话”及其依据，并能展开核对同一任务链的历史版本。

### P0：蒸馏结果仍是阶段日志，不是可理解的专长

**实际观察**

已启动的独立 Agent 首页加载成功，但首屏直接展示了如下内容：

- `P1｜会话分析`、`P2｜通用请求`、`P5｜通用请求` 等泛化阶段名；
- 用户截图附带的环境文本；
- 很长的绝对文件路径；
- 同一类“技能、mcp 与独立 agent 封装”多次重复；
- “这次要完成什么”只显示“给我继续升级方案”，没有把最终目标凝练为可执行任务。

这与用户期待的“能力 / 什么时候使用 / 执行方法”不同。当前输出保留了证据，但没有把证据**蒸馏成决定、方法、输入、交付物和验证标准**。

**必须重构为**

1. 在分阶段之前进行语义归并：去掉环境注入、截图描述、重复请求和纯确认语；把连续纠正合并为最终约束。
2. P 阶段名称应来自“目标 + 产物 + 方法”，例如：
   - `P1｜会话取证与工具轨迹建模`
   - `P2｜多会话能力归并与版本判定`
   - `P3｜Skill、MCP、独立 Agent 一体化交付`
   - `P4｜新手路径、可选择文件与本地执行闭环`
3. 首页默认呈现 3 列能力卡：**能力**、**什么时候使用**、**执行方法与交付物**；原始 P 阶段、文件路径和工具轨迹收进“查看证据”。
4. 每个能力卡都必须有来源数量、最后纠正、相关文件、成功验证和缺失证据，不允许只显示“通用请求”。
5. 把“给我继续升级方案”解析为延续前一目标的指令，不得作为能力包的最终业务目标。

**验收标准**

任意一条会话生成后，首页前三屏不出现“通用请求”、环境注入片段或裸绝对路径；用户能用不看原对话的方式说出这个包能做什么、需要什么输入、会留下什么结果。

### P0：生成后的包难找，重复包难分

**实际观察**

- 主工作台已生成包区域实际有 **24** 张产物卡片。
- 多个包标题重复，例如同一“营销洞察、报告生成与升级...”标题出现 3 次；另一类标题出现 11 次。
- 每张卡片显示很长的描述和保存目录，首屏没有“当前刚生成的包”固定入口，也没有按主题、时间、状态筛选或折叠重复版本。

**用户后果**

用户完成“生成”后仍会问“在哪里看”。这正是历史反馈中反复出现的交付发现问题。

**必须重构为**

1. 生成成功页只显示一个明确结果：包名称、语义简介、三类产物状态、`立即打开独立界面`、`下载 ZIP`、`查看安装说明`。
2. 历史库单独进入“我的能力包”，支持按项目、目标、时间、状态、类型过滤，并将相同语义包折叠成版本栈。
3. 每次包生成都写入 `version`、`sourceConversationIds`、`semanticFingerprint` 和 `latest=true/false`，禁止依赖目录名和时间戳区分。
4. 生成完成后自动滚动/聚焦结果，并提供复制目录和打开目录的次级操作。

**验收标准**

生成完成后，用户无需滚动、无需辨认目录名，在一个页面内可打开刚生成的独立 Agent；历史库中同一主题默认只显示最新版本。

### P1：新手引导存在，但关键决策仍过早暴露

**实际观察**

蒸馏器有三步提示和“新手只需三步”，这是正确基础；但用户刚选择会话就同时看到项目目录、导入文件、粘贴文本、模型地址、模型名称、密钥、包标题、包动作、包用途和三种交付方式。对于没有模型配置经验的用户，这些选项会掩盖主任务。

独立 Agent 的当前已生成版本还保留了可编辑的“项目文件夹”文本框，没有“选择文件夹”按钮。即使最新模板已加入文件夹选择能力，历史已生成包不会自动升级，用户实际打开旧包时仍必须手输路径。

**必须重构为**

1. 默认路径只保留：`选择会话` -> `确认推荐` -> `生成`。
2. 项目、模型、导入文件和自定义包名收进“高级设置”；只有用户需要时展开。
3. 所有本地路径在**新包与历史包**中都使用选择器。为旧包提供“升级到当前运行时”或“重新生成兼容版本”动作，不能只修模板。
4. “自动连接当前 Codex”要显示检查步骤、成功后的模型名称、失败原因和手动设置入口，而非只给一个不可预期的按钮。

### P1：独立 Agent 信息密度过高，移动端只能滚动阅读

**实际观察**

当前独立 Agent 首屏完整初始化后，页面高度从 1,644 px 增至 **8,807 px**；在 390 x 844 移动视口下达到 **12,427 px**。页面没有横向溢出，但模型设置、工作区权限、任务输入和阶段卡片连续堆叠，用户需要长距离滚动才能到达真正的执行输入。

**必须重构为**

1. 首屏只展示：包能做什么、推荐的第一个任务、开始按钮、当前准备状态。
2. 设置做成可折叠的“连接模型”和“选择工作区”两张紧凑面板；准备完成后自动收起。
3. 能力、项目知识、原始证据、任务记录改为真正的分页面或抽屉，不在首页同时渲染。
4. 在移动端提供固定的“开始任务”栏与当前准备状态，避免滚到页面底部才能执行。

### P2：真实数据中的完成状态和证据强度没有参与推荐

当前会话卡显示 `first-user-request`、时间和体积，但没有显示：是否完成、是否产生文件变更、是否通过验证、是否有关联项目、是否被后续会话替代。蒸馏器明明拥有工具调用和项目证据，应把这些信息变成推荐依据，而不是只作为最终报告的原始材料。

建议的推荐分数：

`推荐分 = 语义匹配 + 完成/验证证据 + 最近纠正权重 + 项目关联度 - 重复/中断惩罚`

页面必须用直白中文展示理由，例如：“推荐：同一项目的最新完成版本，包含 4 次文件修改和 3 项验证；早期 11 个重复会话已折叠。”

## 体验重构优先级

| 顺序 | 交付 | 解决的问题 |
| --- | --- | --- |
| 1 | 统一会话索引、语义标题、任务链聚类、全量搜索 | 让用户选对会话。 |
| 2 | 语义蒸馏模型：去噪、合并纠正、能力三栏卡片、证据折叠 | 让用户看懂能力包。 |
| 3 | 生成成功页、能力包版本库、直接打开当前 Agent | 让用户找得到产物。 |
| 4 | 三步新手路径、设置渐进展开、旧包运行时升级 | 让用户能无路径输入地启动。 |
| 5 | 独立 Agent 首页分层与移动端固定执行入口 | 让用户真正开始执行。 |

## 下一轮可用性验收脚本

1. 在 900+ 条会话中搜索业务目标，系统在 30 秒内给出不超过 5 条的语义结果和“为什么推荐”。
2. 选择一条推荐会话后，用户先看能力卡，再按需展开原始证据；不需要阅读会话编号、截图元信息或绝对路径。
3. 点击生成后，结果页立即出现“打开独立界面”，并能解释 Skill、MCP、Agent 各自用途。
4. 在全新 Windows 用户环境中，从选择会话到启动 Agent 不要求手动输入本地文件路径。
5. 在 390 x 844 视口中，首个“开始任务”按钮、准备状态和工作区选择均在三屏内可达。
6. 针对同一主题连续生成三次，历史库只默认显示最新版，旧版可展开、可比较、可恢复。

## 调研结论

目前的基础能力已经足以做“真正的 Codex 工作流复用”：会话、工具、项目文件、验证记录和独立执行台都在。下一阶段不应继续堆叠按钮、阶段和原始证据，而应把现有信息变成**会话推荐 -> 语义能力 -> 明确交付 -> 立即执行**这一条短路径。优先修复选择、蒸馏和结果发现，才能让后续的本地命令、文件修改、模型接入和多项目理解被用户实际使用。
